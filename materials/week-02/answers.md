# Ответы и разбор второй недели

Сначала выполните [самопроверку](quiz.md). Каждый вопрос оценивается независимо; максимальный итог 20.

## Основы · 8 баллов

### Что означает SRP?

Верно: 2. Одна причина изменения, связанная с обязанностью класса

Тариф, драйвер сканера и хранение меняются по разным причинам. Согласование их вызовов — отдельная обязанность терминала.

### У тарифного сервиса высокая cohesion, если…

Верно: 1. Его методы посвящены тарифным правилам

Cohesion описывает смысловую цельность внутри модуля, а coupling — его зависимости от других модулей.

### Где выбирают новый способ оплаты при расширении по OCP?

Верно: 3. В точке сборки, передавая новую стратегию терминалу

Новая реализация PaymentStrategy подключается при сборке. Терминалу достаточно общего process(amount).

### Сигнатуры методов одинаковы. Достаточно ли этого для LSP?

Верно: 1. Нет, нужно сохранить смысл контракта и обещания клиенту

Подстановка требует совместимого поведения: допустимые суммы, смысл True/False и сохранение состояния при отказе.

### Какой контракт нужен клиенту, который только проверяет право проезда?

Верно: 2. Только is_valid()

Узкий контракт не заставляет бесплатный проездной имитировать списание денег.

### Как терминал зависит от репозитория по DIP?

Верно: 3. Принимает контракт record_success(card_id, amount)

Высокоуровневый сценарий не знает, как устроено конкретное хранилище; реализацию выбирают снаружи.

### Что является внедрением зависимости через конструктор?

Верно: 2. TransitTerminal(..., repository=repo, ...)

DI — передача готовой зависимости извне. DIP описывает направление зависимостей; это связанное, но другое понятие.

### Что гарантирует аннотация Protocol при обычном запуске Python?

Верно: 1. Она не проверяет смысл поведения автоматически

Protocol описывает структурный контракт для инструментов типов. Поведение нужно реализовать и проверить тестами.

## Случай 1 · Новый способ оплаты · 3 балла

### Нужно добавить Bluetooth. Какое изменение сохраняет выбранную точку расширения?

Верно: 2. Написать BluetoothPayment.process и передать экземпляр в терминал

Расширяется набор стратегий, а общий сценарий остаётся тем же. Изменение точки сборки допустимо.

### Новая стратегия возвращает строку "False" при отказе. Что увидит if not payment.process(amount)?

Верно: 3. Непустая строка истинна: терминал ошибочно продолжит успех

Нужен bool False, а не строка. Одинаковое имя метода не исправляет нарушенный контракт.

### Как подтвердить совместимость нового способа с терминалом?

Верно: 1. Прогнать общий сценарий успеха и отказа через тот же TransitTerminal

Наблюдайте возврат, записи и сигналы: новый способ должен соблюдать ожидания клиента.

## Случай 2 · Отказ оплаты · 3 балла

### Что возвращает process_tap()?

Верно: 2. False

Отказ оплаты завершает сценарий с False до записи успешной транзакции.

### Сколько успешных записей останется?

Верно: 3. 0

record_success вызывается только после принятой оплаты.

### Какие сигналы получит пользователь?

Верно: 1. Красный индикатор и один сигнал ошибки; успешных сигналов 0

При отказе вызываются show_red и beep_error, затем немедленный return False.

## Случай 3 · Сканер не готов · 3 балла

### Нужно ли вызывать scan_card() после такого is_ready()?

Верно: 2. Нет, сценарий уже отклонён

Ранняя проверка готовности завершает сценарий до чтения карты, расчёта тарифа и оплаты.

### Сколько вызовов process(amount) ожидается?

Верно: 3. 0

Неготовое устройство не должно инициировать оплату.

### Какой тест обнаружит скрытую попытку списания?

Верно: 1. Подставить payment со счётчиком и проверить calls == [] после отказа

Одного возврата недостаточно: счётчик подтверждает отсутствие побочного эффекта оплаты.

## Случай 4 · Сборка и тестируемость · 3 балла

### Где создавать конкретные Scanner, Payment и Repository?

Верно: 1. В точке сборки demo/bootstrap

Точка сборки знает конкретные классы и соединяет их. Терминал знает только нужные операции.

### Зачем передавать SpyPayment в тест?

Верно: 2. Чтобы наблюдать вызовы и задать результат без внешней службы

Тестовый двойник делает сценарий воспроизводимым и позволяет проверить переданную сумму и число вызовов.

### Гарантирует ли учебный process_tap атомарность при сбое хранилища после оплаты?

Верно: 3. Нет, для этого нужны отдельные правила ошибок и согласования

Модель проверяет bool-отказ оплаты и неготовый сканер. Исключения внешних служб и атомарность в её контракт не входят.
