# Лекция 2. Архитектурный порядок и SOLID

**Неделя 2 · 1 час.** Примерная разбивка по минутам дана в [плане лекции](README.md). Это авторский конспект на основе исходных лекций 4–5 и темы со скрина преподавателя.

## 1. Зачем нужны принципы проектирования · 0–8 минут

Класс может правильно хранить баланс и всё равно быть неудобным для развития. Представим терминал, который читает NFC-карту, рассчитывает тариф, списывает деньги, пишет SQL и включает звук. Изменение любого из этих механизмов затрагивает один и тот же класс. Такой класс часто называют **God Object** — объект, в котором сосредоточено слишком много обязанностей.

Синтаксис ООП описывает классы и методы. Проектирование отвечает на другой вопрос: как распределить обязанности и зависимости, чтобы изменения оставались понятными и локальными.

**Cohesion — внутренняя связанность:** насколько методы и данные одного модуля работают на общую цель. У тарифного сервиса высокая cohesion, если его методы посвящены тарифным правилам. Отправка SMS и управление звуком внутри него снижают смысловую цельность.

**Coupling — внешнее зацепление:** насколько модуль зависит от деталей других модулей. Если терминал знает SQL-схему таблиц, смена базы данных заставляет менять терминал. Зависимость от узкого контракта сохранения транзакции уменьшает зацепление с устройством базы.

Ориентир — высокая внутренняя связанность и низкое внешнее зацепление. Это не требование убрать все зависимости или раздробить каждый метод в отдельный файл. Компоненты по-прежнему взаимодействуют; важно, какие детали они обязаны знать.

## 2. SRP — Single Responsibility Principle · 8–18 минут

**У класса должна быть одна причина для изменения.** Практический способ найти эту причину — спросить, чьи требования меняют класс. Такой источник требований называют актором: например, бухгалтерия меняет тарифы, команда оборудования — драйвер NFC, разработчик хранилища — формат записи.

```python Пример смешения обязанностей
class Validator:
    def read_card(self): ...
    def calculate_fare(self): ...
    def save_to_sqlite(self): ...
    def play_sound(self): ...
```

Здесь один класс отвечает на несколько независимых причин изменения. Разделение может выглядеть так:

| Компонент | Обязанность | Что вызывает изменение |
|---|---|---|
| CardScanner | Получить идентификатор карты | Протокол оборудования |
| FareService | Рассчитать стоимость | Тарифные правила |
| TransactionRepository | Сохранить результат | Способ хранения |
| Indicator и Buzzer | Сообщить результат | Визуальный или звуковой канал |
| TransitTerminal | Согласовать последовательность | Сам сценарий обработки прохода |

Терминал вызывает другие компоненты, но не реализует их внутреннюю работу. Оркестрация — самостоятельная обязанность. SRP не означает «один метод»: репозиторий может содержать несколько методов, относящихся к одной задаче хранения.

**Divergent Change** — один модуль меняют по разным причинам. **Shotgun Surgery** — одно требование заставляет править много разрозненных мест. Разделение обязанностей помогает, когда границы выбраны по смыслу изменений; механическое создание множества маленьких классов само по себе проблему не решает.

## 3. OCP — Open/Closed Principle · 18–28 минут

**Код открыт для расширения и закрыт для модификации** в выбранной точке расширения. Для терминала такой точкой может быть способ оплаты.

```python До выделения контракта
def pay(mode, amount):
    if mode == "card":
        return pay_by_card(amount)
    if mode == "qr":
        return pay_by_qr(amount)
    raise ValueError("Неизвестный способ")
```

Новый способ добавляет очередную ветку в обработчик. Вместо этого терминал может принимать объект с общим контрактом:

```python Контракт стратегии оплаты
from decimal import Decimal
from typing import Protocol

class PaymentStrategy(Protocol):
    def process(self, amount: Decimal) -> bool: ...

def pay(method: PaymentStrategy, amount: Decimal) -> bool:
    return method.process(amount)
```

Клиенту важна операция process, а не конкретный класс. В адаптации договоримся: amount — конечный неотрицательный Decimal; True означает принятую оплату, False — отклонённую. Конкретные реализации должны соблюдать этот смысл.

Карта, QR и новый Bluetooth реализуют один контракт. Код pay сохраняется; точка сборки выбирает нужную стратегию. Изменение конфигурации или создание нового класса допускается. OCP не запрещает исправлять ошибки и пересматривать сам контракт при новых требованиях. Он уменьшает область изменений, но не гарантирует отсутствие регрессий.

В Python Protocol описывает структурный контракт для проверки типов: явное наследование от него необязательно. Аннотация сама не проверяет поведение объекта во время выполнения; контракт подтверждают реализация, проверка типов и проверки поведения.

## 4. LSP — Liskov Substitution Principle · 28–38 минут

**Замена объекта другим, поддерживающим тот же контракт, должна сохранять обещания клиентскому коду.** Совпадение имён методов и факт наследования ещё не доказывают корректность замены.

Предусловия — что клиент обязан обеспечить до вызова. Постусловия — что реализация гарантирует после него. Подтип не должен усиливать предусловия, ослаблять постусловия или нарушать инварианты базового контракта.

Пример: контракт принимает любую конечную неотрицательную сумму. Наследник, который внезапно разрешает оплату только от 1000 тенге, усиливает предусловие. Если правило — отклонять такую оплату с False, произвольное исключение вместо этого тоже нарушает обещание клиенту.

В исходной теме рассматривается социальный бесплатный проездной. Ошибочное решение — наследовать его от платной карты и сделать charge всегда бросающим ошибку: клиент платной карты рассчитывает на возможность списания в допустимых условиях.

```python Разные возможности — разные контракты
from decimal import Decimal
from typing import Protocol

class PassVerificationProtocol(Protocol):
    def is_valid(self) -> bool: ...

class BalanceChargeableProtocol(Protocol):
    def charge(self, amount: Decimal) -> bool: ...

def can_enter(document: PassVerificationProtocol) -> bool:
    return document.is_valid()
```

Стандартная карта может поддерживать оба контракта, социальный проездной — только проверку права на проезд. Функция can_enter работает с обоими, поскольку не запрашивает отсутствующую возможность списания. Это изменение модели возможностей, а не попытка заставить бесплатный документ имитировать платную карту.

LSP относится и к структурным контрактам. Реализация с правильной сигнатурой, но неправильным смыслом результата всё равно нарушает ожидания клиента.

## 5. ISP — Interface Segregation Principle · 38–46 минут

**Клиент не должен зависеть от операций, которые ему не нужны.** Контракт «умного оборудования» с чтением карты, печатью чека, обновлением прошивки и воспроизведением звука заставляет простой сканер изображать чужие обязанности.

Разделим возможности по ролям:

```python Узкие протоколы оборудования
from typing import Protocol

class CardScannerProtocol(Protocol):
    def scan_card(self) -> str: ...
    def is_ready(self) -> bool: ...

class VisualIndicatorProtocol(Protocol):
    def show_green(self) -> None: ...
    def show_red(self, reason: str) -> None: ...

class AudioBuzzerProtocol(Protocol):
    def beep_success(self) -> None: ...
    def beep_error(self) -> None: ...
```

Один физический прибор может реализовать несколько протоколов. Разделение касается зависимостей клиентов: компонент, которому нужен только звук, получает AudioBuzzerProtocol. Ему не требуется знать о сканировании карты или обновлении прошивки.

SRP рассматривает причины изменения реализации. ISP рассматривает набор операций, от которых зависит конкретный клиент. Они дополняют друг друга, но отвечают на разные вопросы.

## 6. DIP и Dependency Injection · 46–56 минут

**DIP — Dependency Inversion Principle:** высокоуровневая политика не должна зависеть от конкретных низкоуровневых деталей; обе стороны опираются на абстракции. Детали реализуют потребности политики.

Для терминала политика — последовательность действий при проходе. NFC-драйвер, SQLite и звук — детали. Если терминал сам создаёт SqliteRepository и WindowsBuzzer, он связывает сценарий с конкретной средой. Если он принимает подходящие контракты, сборку можно заменить.

**DI — Dependency Injection:** готовые зависимости передаются объекту извне. Например, через конструктор:

```python Передача зависимостей через конструктор
class Terminal:
    def __init__(self, scanner, payment, repository):
        self._scanner = scanner
        self._payment = payment
        self._repository = repository
```

DIP описывает направление архитектурных зависимостей. DI описывает механизм передачи объектов. Можно передавать конкретный SQLite-класс извне и получить DI, но сохранить сильную зависимость от его SQL-интерфейса. Для DIP терминал должен говорить на языке нужного ему контракта, например record_success, а не execute_sql.

**Composition Root — точка сборки:** место запуска приложения, где создаются конкретные реализации и соединяется граф объектов. В нашем полном примере это функция bootstrap. Создание объектов здесь ожидаемо; терминал получает уже собранные зависимости.

Для небольшого приложения достаточно ручной сборки. DI-контейнер автоматизирует регистрацию и получение объектов при более сложном графе, но не является обязательным условием DIP или DI.

| Время жизни в контейнере | Поведение |
|---|---|
| Singleton | Один экземпляр на регистрацию в конкретном контейнере |
| Transient | Новый экземпляр при каждом resolve |

Singleton в контейнере не обязан быть глобальным объектом всего процесса. Например, два контейнера могут иметь два независимых in-memory репозитория.

**Service Locator:** если терминал получает контейнер и сам вызывает resolve, его реальные зависимости скрыты внутри методов. Constructor Injection делает их явными в конструкторе. Получение корневого объекта контейнером в точке сборки не превращает остальные классы в Service Locator.

## 7. Принципы вместе: терминал Avtobys · 56–60 минут

Поток полного демонстрационного примера: проверить готовность сканера → получить карту → рассчитать тариф → вызвать стратегию оплаты → сохранить успешную транзакцию → сообщить результат.

- SRP: расчёт, хранение, оплата и оборудование разделены; терминал согласует сценарий.
- OCP: новая стратегия оплаты подключается в bootstrap без изменения process_tap.
- LSP: стратегии принимают одинаковые допустимые суммы и одинаково трактуют bool; проездные подставляются в контракт проверки права на проезд.
- ISP: сканер, экран и звук имеют отдельные протоколы.
- DIP: терминал аннотирован контрактами; демонстрационные реализации соответствуют им.
- DI: bootstrap передаёт конкретные объекты в конструктор терминала.

В раскрывающемся блоке под конспектом доступен полный код с кнопкой копирования. Его также можно [скачать как solid_demo.py](examples/solid_demo.py). Пример полностью предоставлен для разбора и не является лабораторным заданием.

Для необязательного запуска сохранённого файла используется Python 3.12+; сторонних библиотек нет:

```powershell Терминал · запуск демонстрации
python solid_demo.py
```

Ожидаемый вывод:

```text
Карта: True
QR: True
Отказ: False
Транзакций: 2
Успешных сигналов: 2
Сигналов отказа: 1
Право на проезд: [True, True]
```

Все реализации оборудования и оплаты в примере — имитации в памяти. Статусы и список транзакций показывают взаимодействие объектов. В примере не реализованы реальные банковские списания, сетевые повторы и согласованность платежа с постоянным хранилищем: эти вопросы требуют отдельного контракта. Отказ оплаты здесь не создаёт успешную запись.

Главная идея лекции: границы объектов выбираются по обязанностям и обещаниям клиентам. Абстракции полезны там, где есть понятная изменяемая деталь; дополнительный интерфейс без такого смысла только усложняет чтение.
