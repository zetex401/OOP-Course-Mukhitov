## 1. Зачем нужны объекты: начнём с поломки

В транспортной системе карта хранит баланс и признак блокировки. Пока данных мало, удобно написать:

```python
card = {"id": "KZ-01", "balance": 250, "blocked": False}
card["balance"] -= 300
```

Код выполняется, но баланс становится -50. Правило «баланс неотрицателен» осталось только в голове разработчика. Можно добавить `if` перед списанием, но другой участок программы забудет его повторить. Переименование ключа словаря тоже придётся согласовывать со всеми читателями.

Проблема не в том, что словари или функции плохи. Они подходят, например, для простых промежуточных данных. В этой задаче важно, чтобы правила изменения состояния имели одного ответственного. Таким ответственным станет объект карты.

**Вопрос на минуту:** где должна находиться проверка баланса, чтобы каждый вызов оплаты проходил через неё?

## 2. Класс, экземпляр, состояние и поведение

Класс описывает, какие данные и действия есть у объектов. Экземпляр - конкретный созданный объект.

```python
class Passenger:
    def __init__(self, name: str):
        self.name = name

    def greeting(self) -> str:
        return f"Привет, я {self.name}"

first = Passenger("Алия")
second = Passenger("Данияр")
print(first.greeting())  # Привет, я Алия
```

- `Passenger` - класс; `first` и `second` ссылаются на разные экземпляры.
- `__init__` задаёт начальное состояние уже создаваемого экземпляра; в учебной речи это часто называют конструктором.
- `self` обозначает текущий экземпляр. При `first.greeting()` Python передаёт его в метод автоматически.
- `name` - атрибут состояния; `greeting()` - поведение.
- `-> str` и `name: str` описывают ожидаемые типы, но сами по себе не проверяют аргументы во время исполнения.

Равное состояние не означает, что объекты одни и те же: два пассажира могут иметь одинаковое имя. `a is b` проверяет, ссылаются ли переменные на один объект. Доменный `card_id` - идентификатор карты в нашей модели; это не адрес памяти Python. Уникальность ID среди всех карт отдельный класс сам по себе не обеспечивает.

Для Avtobys получаются такие кандидаты:

| Объект | Пример состояния | Поведение |
|---|---|---|
| Route | номер, остановки, тариф | предоставлять проверенные данные маршрута |
| Bus | номер, вместимость, пассажиры, маршрут | посадка, высадка, назначение маршрута |
| TransitCard | ID, баланс, скидка, блокировка | пополнение, оплата, блокировка |
| SingleTripTicket | код, цена, время покупки, использован ли | однократная валидация |

Это четыре класса для учебной модели, а не требование реализовать настоящую платёжную систему.

## 3. Инвариант - правило, которое нельзя потерять

Инвариант - условие допустимого состояния объекта. Оно должно быть истинно после успешной инициализации и после завершения его публичных операций. Если операция отвергнута, допустимое состояние также должно сохраниться.

Примеры:

- У карты `balance >= 0`.
- У автобуса `0 <= current_passengers <= capacity`.
- У маршрута хотя бы две остановки и нет одинаковых соседних остановок.
- Использованный билет не может стать неиспользованным через публичный интерфейс.

Правило «заблокированная карта отклоняет оплату» описывает допустимое поведение; вместе с ограничениями состояния оно входит в контракт объекта.

**Порядок действий важен:** сначала проверить возможность операции, затем изменить состояние. Не списывайте деньги в минус с намерением позднее вернуть их после исключения.

```python
# Принцип, не полный класс:
if balance < amount:
    raise InsufficientFundsError("Недостаточно средств")
# Изменение происходит только после всех проверок.
balance -= amount
```

## 4. Инкапсуляция не сводится к геттерам и сеттерам

Инкапсуляция объединяет данные с поведением и ограничивает способы изменения состояния. Сокрытие деталей помогает клиенту не зависеть от внутреннего хранения.

Плохо для нашей задачи:

```python
if not card.is_blocked and card.balance >= fare:
    card.balance = card.balance - fare
```

Здесь клиент знает правила и сам управляет балансом. Лучше:

```python
paid = card.pay(fare)
```

Карта сама проверит блокировку, скидку и остаток. Это идея **Tell, Don't Ask**: попросите объект выполнить осмысленное действие. Она не запрещает чтение свойств для интерфейса или отчёта: показать `card.balance` нормально, менять баланс в обход операции - нет.

Геттер для чтения баланса полезен. Общий сеттер `balance = любое_значение` может разрушить модель: он не объясняет, откуда появились деньги и почему операция разрешена. Предпочтительнее `top_up()` и `pay()` с понятными правилами.

## 5. Как это выглядит в Python

```python
from decimal import Decimal

class Balance:
    def __init__(self, initial: Decimal):
        if not isinstance(initial, Decimal):
            raise TypeError("Нужен Decimal")
        if not initial.is_finite() or initial < 0:
            raise ValueError("Нужен конечный неотрицательный баланс")
        self._value = initial

    @property
    def value(self) -> Decimal:
        return self._value

balance = Balance(Decimal("250.00"))
print(balance.value)  # 250.00
# balance.value = Decimal("-1.00") вызовет AttributeError.
```

`@property` позволяет читать значение как атрибут. Без сеттера присваивание публичному свойству запрещено. Но `_value` - **соглашение о непубличном поле**, а не защита от намеренного вмешательства: `balance._value = ...` технически возможно. Даже двойное подчёркивание в Python не является механизмом безопасности. Мы защищаем нормальное использование публичного интерфейса и проверяем контракт, а не строим песочницу.

Ещё одна ловушка: сохранить список остановок и вернуть его наружу - значит оставить обход инварианта. Клиент сможет очистить его через `.clear()`. В примере решения входной список копируется в `tuple`, который выдаётся только для чтения. Это маленькая мера для конкретного инварианта, а не универсальный слой архитектуры.

## 6. Почему деньги - Decimal

```python
from decimal import Decimal

print(0.1 + 0.2 == 0.3)  # False
print(Decimal("0.1") + Decimal("0.2") == Decimal("0.3"))  # True
```

Двоичный `float` не представляет многие десятичные дроби точно. `Decimal` удобен для явных десятичных денежных правил. Создавайте его из строки: `Decimal("0.1")`, а не из уже неточного `float`.

В нашем задании суммы задаются конечными Decimal-значениями, кратными 0.01 KZT. `NaN` и бесконечность - не допустимые деньги. Эти проверки - уточнение учебного контракта, чтобы сравнения не пропускали некорректные значения.

Скидка обозначает долю, которую **не платят**:

```text
к оплате = базовый тариф * (1 - discount_rate)
```

| Базовый тариф | Скидка | К оплате |
|---:|---:|---:|
| 100.00 | 0 | 100.00 |
| 100.00 | 0.5 | 50.00 |
| 100.00 | 1 | 0.00 |

В плохом процедурном примере лекции используется умножение непосредственно на скидку. Не переносите эту строку в решение: для смысла скидки из лабораторной границы 0 и 1 требуют формулы выше. В эталоне итог округляется до 0.01 через `ROUND_HALF_UP`; это явное правило адаптации, не утверждение о реальных тарифах Avtobys.

## 7. Исключения объясняют отказ

`False` сообщает об отказе, но не отличает блокировку карты от нехватки денег. В предметной модели удобно различать:

- `InsufficientFundsError` - недостаточно средств;
- `CardBlockedError` - операция запрещена из-за блокировки;
- `CapacityExceededError` - автобус переполнится;
- `TicketAlreadyUsedError` и `TicketExpiredError` - билет нельзя использовать.

Для неверного значения аргумента подходит `ValueError`, для неверного типа - `TypeError`. Обработку ошибок и пользовательские сообщения пишите снаружи модели:

```python
try:
    paid = card.pay(Decimal("100.00"))
except CardBlockedError:
    print("Карта заблокирована")
except InsufficientFundsError:
    print("Пополните баланс")
```

Аннотации типов помогают читателю и инструментам, но эти проверки не заменяют. В Python `bool` является подклассом `int`; для количества пассажиров в нашей модели проверяем `type(count) is int`, чтобы `True` не считалось одним пассажиром.

## 8. Богатая и анемичная модель: выбирайте по ответственности

Класс с полями и внешним сервисом, который делает все проверки, в рассматриваемом домене оказывается анемичным: правила легко обойти или продублировать. Богатая модель помещает правила допустимых изменений рядом с состоянием.

Это не означает, что каждый набор данных обязан иметь десятки методов. Для простого сообщения между функциями структура данных может быть достаточной. Выбор модели объясняйте конкретным правилом и риском, а не количеством классов.

## 10. Отношения объектов и композиция

Зависимость Uses-A возникает, когда метод использует другой объект. Ассоциация Has-A связывает объекты; агрегация позволяет компоненту существовать независимо, композиция связывает его жизненный цикл с владельцем. Наследование Is-A подходит для подстановки по общему контракту. Комбинации вроде StudentSuburbanFare создают рост иерархии: скидку, зону и время удобнее соединять как независимые политики.

В примере калькулятор получает политику скидки через конструктор. Новая политика реализует тот же контракт, поэтому код расчёта не меняется. Protocol описывает структурный контракт; классу достаточно подходящего метода. Его аннотация сама не проверяет объект во время исполнения.

```python
from decimal import Decimal
from typing import Protocol


class DiscountPolicy(Protocol):
    def discount(self, fare: Decimal) -> Decimal: ...


class StandardDiscountPolicy:
    def discount(self, fare: Decimal) -> Decimal:
        return Decimal("0.00")


class StudentDiscountPolicy:
    def discount(self, fare: Decimal) -> Decimal:
        return fare * Decimal("0.5")


class FareCalculator:
    def __init__(self, discount_policy: DiscountPolicy):
        self.discount_policy = discount_policy

    def calculate(self, fare: Decimal) -> Decimal:
        return fare - self.discount_policy.discount(fare)


assert FareCalculator(StandardDiscountPolicy()).calculate(Decimal("100.00")) == Decimal("100.00")
assert FareCalculator(StudentDiscountPolicy()).calculate(Decimal("100.00")) == Decimal("50.00")
```

Проверьте две суммы. Объясните, как два калькулятора могут использовать одну политику: это совместно используемый независимый компонент. Полный движок со скидками, зонами, временем и округлением остаётся заданием [лабораторной 2](../../.tfw/COURSE-MATERIALS/02_Лабораторная_02_Композитный_движок_тарификации_и_платежей.pdf).

## 11. Полиморфный вызов и явный контракт

Полиморфизм позволяет клиенту вызывать один метод у разных реализаций без ветвления по конкретному классу. Duck Typing опирается на доступное поведение, ABC задаёт номинальный абстрактный базовый класс и не позволяет создать экземпляр с нереализованным абстрактным методом, Protocol описывает структурное соответствие. Выбор контракта зависит от задачи; одинаковое имя метода ещё не гарантирует одинаковый смысл.

В компактном примере из темы исходного комплекта 3 диспетчер доставляет одно неизменяемое событие обработчикам общего контракта. Падение одного обработчика сохраняется как ошибка и не прерывает аудит.

```python
from dataclasses import dataclass
from decimal import Decimal
from typing import Protocol


@dataclass(frozen=True)
class CardTapEvent:
    card_id: str
    amount: Decimal


class EventHandler(Protocol):
    def handle(self, event: CardTapEvent) -> None: ...


class AuditLogHandler:
    def __init__(self):
        self.audit_records: list[CardTapEvent] = []

    def handle(self, event: CardTapEvent) -> None:
        self.audit_records.append(event)


class FailingHandler:
    def handle(self, event: CardTapEvent) -> None:
        raise RuntimeError("Сбой уведомления")


class EventDispatcher:
    def __init__(self):
        self.handlers: list[EventHandler] = []
        self.errors: list[str] = []

    def subscribe(self, handler: EventHandler) -> None:
        self.handlers.append(handler)

    def dispatch(self, event: CardTapEvent) -> int:
        delivered = 0
        for handler in self.handlers:
            try:
                handler.handle(event)
                delivered += 1
            except Exception as error:
                self.errors.append(str(error))
        return delivered


dispatcher = EventDispatcher()
audit = AuditLogHandler()
dispatcher.subscribe(FailingHandler())
dispatcher.subscribe(audit)
event = CardTapEvent("KZ-01", Decimal("50.00"))
assert dispatcher.dispatch(event) == 1
assert audit.audit_records == [event]
assert dispatcher.errors == ["Сбой уведомления"]
```
